# CP23 hardening evidence

CP23 treats reliability as scoped evidence, not a claim that failure is
impossible. Every subcheckpoint records its invariant, attack method, observed
result, and remaining boundary.

## 23.1 - Baseline contracts and threat model

- Invariants: untrusted proxy headers never influence identity or cookie
  security; credentials never enter diagnostics; release replacement is
  checksum-verified and atomic; rollback does not touch instance data.
- Actors: unauthenticated clients, application users, scoped service identities,
  administrators, reverse proxies, storage providers, and operators.
- Trust boundaries: public HTTP, administrator cookies, bearer tokens, SQLite,
  local/S3 objects, webhook/Lambda egress, release downloads, backup archives.
- Evidence: proxy tests, support-bundle redaction tests, six-target release test,
  installer test, and update -> rollback test.
- Boundary: this is an engineering threat model, not an independent security
  assessment. CP23.6 will attack authorization and close remaining threats.

## 23.2 - Input fuzzing

- Invariants: filter input never becomes SQL text; invalid rules never authorize;
  webhook targets require HTTPS, a host, and no URL credentials; malformed Lambda
  targets fail without panic.
- Method: seeded Go fuzz targets plus generated mutations for filters, rules,
  webhook URLs, and Lambda ARNs/regions.
- Result: retained fuzz targets are green for the committed corpus and the
  recorded development campaign. CI preserves their seed corpus as regressions.
- Boundary: the short committed campaign is useful mutation evidence, not proof
  over all inputs or a replacement for CP23.6 authorization abuse testing.

## 23.3 - Concurrency, restart, and failure injection

- Invariants: a durable job is claimed once per attempt; concurrent claimers do
  not duplicate successful execution; expired leases return to the queue after
  interruption; race-enabled request/store/record suites remain clean.
- Method: eight simultaneous workers contend for 64 durable jobs, an interrupted
  running job is recovered from an expired lease, and the affected packages run
  repeatedly under Go's race detector.
- Result: 64/64 jobs completed once with one recorded attempt, lease recovery
  completed on its next claim, and 20 race-enabled package repetitions passed.
- Boundary: this exercises the Go scheduler and SQLite deployment on this host;
  it cannot enumerate every interleaving, kernel, filesystem, or power failure.

## 23.4 - Migration and upgrade fixtures

- Invariants: every retained schema version upgrades to the current version;
  migration history is complete; existing rows survive; SQLite integrity remains
  good; future schemas are refused; failed migrations change neither schema
  version nor prior data.
- Method: construct fixtures at versions 0 through 13, seed a durable probe,
  reopen through the production initializer, and repeat the matrix five times.
  Inject invalid SQL into a version-6 upgrade transaction and inspect rollback.
- Result: 14 fixture paths x 5 repetitions upgraded with complete migration
  history and `PRAGMA integrity_check=ok`; the injected failure retained version
  6 and its prior row; schema version 999 remained refused.
- Boundary: generated schema fixtures prove every retained migration boundary;
  release-binary/platform upgrade compatibility remains part of the final matrix.

## 23.5 - Backup, corruption, restore, and rollback drills

- Invariants: a consistent backup restores database rows and local objects into
  a new owner-only directory; hostile archives never escape staging; corrupt,
  truncated, incomplete, future-schema, and existing-target restores fail without
  publishing partial state; executable rollback leaves data untouched.
- Method: create a real authenticated backup with seeded SQLite and file data,
  restore through `trestle restore`, reopen it, and repeat five times. Generate
  traversal, backslash, missing-database, corrupt-database, future-schema and
  truncated archives, plus an occupied destination. Repeat updater rollback.
- Result: five complete round trips preserved both probes and passed SQLite
  integrity verification. Every hostile case failed before atomic publication;
  update -> rollback restored the prior executable.
- Boundary: local-storage restore is exercised here. S3 object restoration still
  depends on the provider's independently operated versioning/backup procedure.

## 23.6 - Authorization and security abuse

- Invariants: row-owner rules apply identically to list/view/update/delete;
  individual denial does not reveal record existence; refresh tokens cannot act
  as access tokens; service read scope cannot mutate; bearer writes require the
  exact write scope without inheriting browser-cookie CSRF semantics.
- Method: compose the production application-user, credential, rule, collection,
  record and administrator handlers. Create two users, two scoped service actors
  and cross-owned rows; attempt list, direct lookup, mutation, owner forgery,
  token-type confusion and scope escalation. Repeat ten times plus race suites.
- Finding and repair: individual row-rule evaluation previously continued after
  a false result, exposing cross-owner view/update/delete by known ID. The shared
  decision now returns the same 404 as an absent record; lists retain SQL filters.
- Result: all cross-owner and token/scope confusion attempts are denied, own-row
  access remains functional, and race-enabled identity/rule/file/server tests pass.
- Boundary: this is a retained engineering abuse corpus, not an independent
  penetration test or certification.

## 23.7 - Sustained load and resource exhaustion

- Invariants: bounded concurrent reads complete without response amplification
  or goroutine retention; record page/batch limits fail before work expands;
  incomplete slow headers are disconnected by the server timeout.
- Method: seed 100 typed records; issue 1,200 reads from 24 workers per run,
  repeat three times and once under the race detector; attack 1,001-record batch
  and million-row page requests; repeat ten real TCP slow-header connections.
- Result: 4,800 concurrent reads completed with bounded responses and no retained
  goroutine growth; oversized work returned controlled 400/422 responses; all ten
  incomplete clients were disconnected before reaching the handler.
- Boundary: this is a local bounded-load campaign, not a capacity promise for
  every machine, schema, network, storage provider, or hostile distributed load.

## 23.8 - Browser, accessibility, and performance quality

- Invariants: every route retains a visible keyboard focus path and current-page
  semantics; the mobile drawer closes with Escape; long values remain contained;
  reduced-motion preferences are honored; the embedded interface requires no
  inline execution under a strict content policy.
- Method: rebuild the Nift dashboard, run retained structural accessibility and
  responsive assertions, syntax-check the generated JavaScript, exercise server
  security headers, and enforce HTML/CSS/whole-dashboard byte budgets.
- Result: the generated dashboard passes its language, landmark, focus, status,
  drawer, long-content and reduced-motion contracts. Three embedded files total
  less than 320 KiB, with HTML below 24 KiB and CSS below 96 KiB.
- Boundary: structural and keyboard contracts supplement rather than replace
  assistive-technology and browser testing by people using the released product.

## 23.9 - Contract, documentation, and dependency audit

- Invariants: every production environment variable is documented; public links
  resolve; completed functionality is not described as future work; prohibited
  comparison/AI-signature wording does not return; module checksums are intact.
- Method: compare configuration symbols from production source against README and
  public documentation, scan all authored pages for stale release language and
  forbidden wording, validate all 80 generated HTML pages, and verify/list the Go
  module graph.
- Result: all production configuration keys are documented, 80 pages and 84 files
  pass local-link validation, stale pre-hardening status and upgrade claims were
  corrected, and the complete module graph verifies against recorded checksums.
- Boundary: examples describe supported behavior at this commit. Stable versioning
  and release-candidate support boundaries are frozen in 23.10.
