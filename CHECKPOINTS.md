# Trestle implementation handover

This is the executable game plan for taking Trestle from its current scaffold
to a credible first stable release. Work in order. Every checkpoint is intended
to end in reviewable commits with runnable evidence, not a partially connected
layer that only becomes usable several checkpoints later.

## How to use this handover

For each checkpoint:

1. Re-read the affected contract documents and inspect all three repositories.
2. Record any newly discovered ambiguity before choosing an implementation.
3. Implement the smallest complete product slice, including failure behavior.
4. Add the appropriate unit, integration, migration, concurrency, authorization,
   adversarial, browser, and cross-platform tests.
5. Exercise the slice manually through its public boundary, not only internals.
6. Build and inspect the Nift dashboard and public website.
7. Update this checkpoint with commit IDs, commands, results, and known limits.
8. Commit the application repository.
9. When the public site changed, commit its nested generated `public/` repository
   first, then commit the website source repository and its updated gitlink.
10. Finish with every touched repository clean.

Do not call a checkpoint complete if its website copy describes an aspiration as
an implementation, if generated site output is stale, or if the only evidence is
that compilation succeeds.

## Continuous website contract

The sibling `../trestle-dev.github.io` repository is a product deliverable, not a
late marketing task. It must become a multi-page, content-rich public site as the
product grows:

- minimalist authored dark theme, restrained accent, strong typography, and
  readable code/examples;
- vanilla HTML, CSS, and JavaScript generated by Nift - no frontend framework;
- shared header, footer, documentation navigation, page metadata, status labels,
  version notices, and accessible mobile navigation;
- progressive enhancement, useful no-JavaScript content, keyboard support,
  visible focus, reduced motion, good contrast, and responsive layouts;
- documentation spread across task-focused pages rather than one enormous page;
- real commands and screenshots only after they can be reproduced;
- clear **planned**, **experimental**, and **available** labels derived from
  checkpoint evidence;
- no invented adoption, performance, security, compatibility, or availability
  claims.

Every product checkpoint below has a website slice. “Update the website” means
editing Nift source, rebuilding, checking internal links and metadata, inspecting
desktop/mobile output, committing generated output, then committing source.

## Evidence record template

Replace the checkpoint's `Status: pending` line only after the gate passes:

```text
Status: complete
Application commit: <sha>
Website output commit: <sha or n/a>
Website source commit: <sha or n/a>
Verified: <commands and concise results>
Known limits: <honest remaining limits or none>
```

## After the first stable release

Choose subsequent checkpoints from user evidence, not feature resemblance.
PostgreSQL, clustering, view collections, GraphQL, a plugin marketplace, hosted
cloud, and a sandboxed local function worker each require a fresh contract,
threat model, migration story, website slice, and independent exit gate. None is
implicitly promised by the architecture above.
